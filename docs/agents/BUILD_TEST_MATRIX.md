# OTClient Build and Test Matrix

Validation is proportional to changed paths, risk and current milestone. Exact live workflow/preset state is authoritative.

## 1. Greenfield Rust client policy

The Rust client lives under `oteryn-client/`. The foundation audit is merged and the Rust workspace foundation is active through PR #50.

### Documentation and audit changes

| Change | Minimum validation | Additional evidence |
|---|---|---|
| Architecture/ADR | Markdown, link/path and complete diff review | repository fast/docs checks |
| Audit documents | evidence labels, citations/paths, consistency and provenance review | exact external/runtime blockers documented |
| Synthetic fixture inventory | schema/provenance/secret/license review | parser/runtime behavior not claimed until implemented |

Documentation-only changes do not require speculative product compilation, but any change under a Rust workflow path still follows the live emitted check graph.

### Rust workspace and crate changes

Run from `oteryn-client/` using the pinned toolchain and committed lockfile:

```text
cargo metadata --locked --format-version 1
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --all-targets --locked
cargo run --locked -p oteryn-architecture-check -- workspace .
cargo deny check
```

| Rust change | Required focused evidence | Exact-head CI evidence |
|---|---|---|
| Workspace/toolchain/manifest/lockfile | locked metadata, formatting, Clippy, tests and architecture policy | `Rust Client / Windows` plus supply-chain job |
| Architecture category/edge | valid fixture and focused invalid fixture with expected stable rule code | real workspace check plus all architecture tests |
| Foundation/domain/runtime crate | crate-local unit/property tests and dependency-boundary proof | Windows workspace build/lint/test and supply-chain policy |
| Diagnostics contract crate | constructor/compile barriers for safe text, bounded event tests and synthetic secret-shaped redaction regressions across `Debug`/`Display` | Windows workspace build/lint/test, architecture validation and supply-chain policy; no sink/runtime compatibility claim |
| Deterministic test-support crate | explicit `ManualClock` reuse, start/advance/backwards/overflow/thread observation, exact context, insertion order, duplicate/bound propagation, synthetic redaction and compile-fail runtime-string barriers | Windows workspace build/lint/doctest, architecture validation and supply-chain policy; no runtime compatibility claim |
| Protocol crate | golden, malformed, truncated, wrong-gate and fuzz-smoke fixtures against an exact producer revision | Windows tests plus exact supported-pair evidence |
| Asset importer/runtime | deterministic synthetic fixtures, corrupt/bomb/path negatives and provenance review | Windows tests, supply-chain check and later clean-install/runtime evidence |
| Renderer/UI | CPU-side tests and original/synthetic scenes | Windows/GPU milestone evidence when runner and target hardware are defined |
| Identity/session | fake-service positive/negative cases, replay/stale callback/secret-redaction tests | Windows integration evidence and exact cross-repository pair |
| Launcher/updater | signature/hash/tamper/interruption/rollback tests | Windows clean install/update/rollback evidence |

Current workspace invariants:

- Windows x86-64 MSVC is the required compiled target;
- unsafe Rust is forbidden by default;
- warnings fail required Clippy CI;
- every workspace package uses an `oteryn-` name and declared architecture category;
- legacy `src/`, `modules/` and `mods/` runtime dependencies are forbidden;
- unknown registries/git sources, wildcard dependencies, duplicate versions and unapproved licenses are denied;
- `Cargo.lock` is committed and must remain generated by the pinned toolchain/dependency resolver;
- no new crate is created without a bounded observable work package and catalogue update;
- diagnostics text must be explicitly classified; sensitive values are redacted at construction and arbitrary runtime text has no implicit safe conversion;
- deterministic test support reuses `ManualClock` directly and must not create another clock, scheduler, executor, sleep loop, global registry or product service.

The supply-chain job may run on Ubuntu using the pinned official cargo-deny action. It does not replace required Windows compilation/testing and does not establish Linux product compatibility.

Planned later stages remain defined by `oteryn-client/docs/architecture/PERFORMANCE_AND_TESTING.md`: protocol corpora, Windows runtime integration, GPU scenes, performance trends and packaging/update acceptance.

## 2. Legacy C++/Lua client policy

Always inspect current `CMakePresets.json`; live PRs may change test presets. Existing policy remains Windows-only for required compilation.

- Primary CI may use Ubuntu for path detection, YAML/static checks, Lua syntax and required-job evaluation, but not to claim Linux client compatibility.
- Required compilation and CTest coverage use the current Windows workflow/presets.
- Linux, macOS, Android, browser and Docker workflows are dormant unless explicitly re-enabled.
- `docs/architecture/LEGACY_OTCLIENT_ARCHITECTURE.md` and `docs/agents/LEGACY_OTCLIENT_WORKSTREAMS.md` preserve detailed owner-specific evidence requirements.

Known release command:

```bat
cmake --preset windows-release
cmake --build --preset windows-release
```

| Legacy change | Minimum local validation | Additional validation |
|---|---|---|
| Documentation/task records | Markdown/path/full-diff review | fast/docs checks; no compilation |
| Lua module/mod | runtime-root syntax/static checks and focused tests | runtime interaction; C++ build only if compiled integration changed |
| OTUI/style | load/parse and interaction | relevant resolution/DPI evidence |
| C++ implementation | focused Windows compile and affected CTest | full required Windows matrix on final head |
| CMake/dependency/public header | configure/build early enough to protect later work | clean Windows final validation |
| Protocol | parser/output tests and exact Canary pair | Windows loopback or real integration |
| Test infrastructure | existing support tests and labels | full affected Windows preset/CTest |
| Asset installer | hash/path/fallback/extraction tests | clean Windows install/runtime load |
| CI workflow | YAML/required-check/path-filter review | observe emitted checks on PR |

## 3. Cross-track changes

A PR should not normally change both legacy runtime code and Rust-client implementation. Shared documentation/contract changes must clearly identify which behavior is proven for which track.

- Legacy build success does not validate the Rust architecture.
- Rust workspace success does not validate legacy C++ behavior.
- Protocol and Identity claims require exact producer/consumer evidence for the affected client implementation.
- Supply-chain or metadata success does not prove runtime/server/GPU compatibility.

## 4. Validation timing

- Run cheap focused checks after coherent edits.
- Run heavy compilation at the end of a coherent implementation package, or earlier when manifests/toolchains/public interfaces change.
- A later build-affecting commit invalidates prior build evidence.
- A ready-for-review transition may emit a second exact-head run; both the live required graph and task-specific Rust jobs must pass before merge.
- Never mark a check passed without exact evidence.

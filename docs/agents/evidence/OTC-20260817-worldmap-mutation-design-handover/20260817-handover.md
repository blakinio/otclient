The exact geometry source chain is:

```text
hardcoded packed 18/14 @ 0x01cdd958
 -> exact TWorldmapProtocolMessageHandler constructor
 -> Handler+0xb0/+0xb4 constructor default
 -> 0x00bc6350 geometry snapshot +0x38
 -> Handler+0x10 exact TWorldMapStorage virtual dispatch
 -> exact TWorldMapStorage slot 12 0x00cc6cd0
 -> Storage+0x48/+0x4c
```

`TWorldMapStorage` is proven extent/coordinate driven. Lower/upper XYZ bounds are half-open, slot 12 replaces geometry and drives out-of-bounds removal, and no fixed maximum Storage/cache capacity was proven. The object carrying retained 18/14 is Storage, not Viewport.

`TWorldMapViewport` is a separate exact object. Its constructor consumes the same packed 18/14 default and later recomputation at `0x00cbf700` derives geometry from Viewport state, including packed 15/11 delta state and signed shift-by-5 / divide-by-32-family arithmetic.

`TWorldMapRenderProvider` exact identity is proven and its primary paths contain fixed-32 clipping/culling/indexing/iteration dependencies, including shift-by-5 and `&0x1f` operations.

`TWorldMapPicker` exact identity is proven and its primary paths contain fixed-32 screen/world conversion and bounds traversal using shift-by-5, `0x1f` correction and `0x20` stepping.

`TWorldMapCamera` exact identity/layout and higher-level co-ownership with a Viewport-compatible object are proven. A bounded exact-vptr sweep did not recover a direct Camera-field -> Storage slot 12 / Handler master-pair mutation edge. This is bounded negative evidence only.

## What this enables

The project no longer needs to ask whether 18x14 is merely an observed rendering accident or where the values enter worldmap state. The source and dependency graph are known well enough to design a controlled larger-extent experiment.

A successful later implementation could potentially provide both:

- a larger actually rendered worldmap area; and/or
- a larger client-resident tile/world-state area available to instrumentation/bridge logic.

Those outcomes are not yet proven. Increasing the packed 18/14 source alone is not sufficient evidence of a correct feature because Viewport, fixed-32 RenderProvider behavior, Picker transforms, Camera coupling and parser/network constraints must remain coherent.

## Explicit carried UNKNOWNs

- semantic interpretation of the RenderProvider `65535 x 10-byte` allocation as a map ceiling;

Required policy:

- prefer an original synthetic fixture produced by a reviewed Canary test seam or a separately implemented bounded fixture builder;
- never retain a live Game Session, password, account identifier, character identity, cookie, endpoint containing private topology, private chat or raw user path;
- replace names and identifiers with deterministic synthetic values before the bytes are considered for commit;
- do not use proprietary Tibia client binaries or asset bytes as fixture sources;
- a public packet capture is not automatically redistributable or sanitized;
- every committed byte file requires a human-readable decoded expectation beside it;
- a fixture generated from a later producer commit must not silently replace the pinned corpus; compatibility is versioned explicitly;
- fixture hashes are regenerated by the fixture-owning task, never copied from an unverified source.

## Required corpus per selected family

Every implemented family requires this minimum set:

1. one representative valid message;
2. the smallest valid message;
3. each maximum bound selected by the Rust contract, using synthetic values;
4. truncation immediately before and inside every variable-length/count-controlled section;
5. invalid count, length, enum/discriminator and checked-conversion cases;
6. wrong profile and wrong feature/build gate where the producer has such a branch;
7. out-of-order or wrong-lifecycle-state delivery;
8. trailing bytes or duplicate message where the protocol state makes them unsafe;
9. round-trip output inspection only when re-encoding is semantically stable;
10. one minimized regression seed for every parser defect found later.

Fuzzing starts from the reviewed synthetic corpus. Fuzz inputs are not promoted to durable regression files until minimized, classified and scrubbed.

## Capability/build-gate fixtures

The Current profile includes material feature gates. A future adapter must add a wrong-gate fixture before implementing each gated payload.

Specific mandatory cases:

- `PlayerDataLevelPercentU16`: a Current fixture proving the centesimal `u16` field and a negative fixture demonstrating rejection of a mismatched legacy-width expectation;
- `GameEventPayload`: one fixture for the selected event selector and one invalid selector/truncation case;
- `GraphicalEffectSourceByte`: no implementation until an exact producer message and client-consumer expectation are jointly proven;
- `OfficialVocationSpecificPlayerData`: fixture per selected MPS vocation branch or explicit suppression until supported;
- `OfficialWeaponProficiencyPayload`: separate fixtures for a recognized detail-list build prefix and an unrecognized synthetic `15.25.*` build that uses the shorter producer branch;
- every deferred Current feature remains unsupported rather than parsed as opaque trailing data unless an explicit bounded skip contract is reviewed.

## Harness requirements for the future implementation task

The fixture owner should provide:

- a pure byte-to-validated-adapter-message parser entry point with input/collection/string/decompression limits;
- a deterministic output inspector for client commands;
- a fake transport that separates framing/crypto/compression tests from message parsing;
- a deterministic session state machine that can assert wrong-order rejection;
- stable error categories that contain no raw external text or payload bytes;
- corpus metadata validation and SHA-256 verification;
- fuzz targets for transport, first-message parsing and each variable-layout family;
- no dependency on the legacy C++ client, its globals, Lua modules or proprietary assets.

## Acceptance gate before any compatibility claim

A future Current-profile adapter may claim a selected family only after:

- the exact producer commit and client build string are recorded;
- field order, widths, signedness, optionals and gates are documented in a shared contract;
- positive and all applicable negative fixtures pass on the exact Rust head;
- the Canary producer-side test or source expectation is linked;
- the full corpus is synthetic or has confirmed redistribution rights;
- no secrets/private data appear in source, metadata, test output or failure formatting;
- the exact supported and unsupported producer/consumer pairs are recorded.

Repository CI success without this evidence is not protocol compatibility proof.
